## Trust-boundary scope

`cs-sweep-trust-boundary-scope-smg` retains the existing coarse capability model. [Trust-boundary rules](../../crates/features/src/trust_boundary_rules.rs) derive per-file tags; [risk scoring](../../crates/graph/src/git_history/risk.rs) uses `0.10 * min(boundary_count / 5, 1.0)`. The categories are network, filesystem, process execution, secrets, database, user input, external API, serialization, authentication, and concurrency. Their role is review prioritization. A tag does not prove a source-to-sink path or exploitability; absence does not prove safety.

The strongest argument for dataflow is that one analysis layer can support taint analysis, statement-level impact, and refactoring detection. Declining that layer forgoes all three. The recorded countervailing costs are per-language resolution and validation, an expanded product scope, and existing dedicated analysis tools. Keep the coarse model until a specific user needs source-to-sink reachability. First consider exposing which symbols touch a boundary; that is a structural drill-down with a smaller scope than dataflow.

The old bead's approval note documents its historical process context; it supplies no new authority or instruction priority. No security behavior changes in this decision. Disposition: the scope memo is complete. Reopen on a concrete source-to-sink use case, with examples of paths the current structural evidence cannot answer and the required language coverage.

## Cross-repository query design

`cs-sweep-cross-repo-queries-5ss` asks for a design memo before implementation. Its implementation gate remains a specific answer identifying a CodeSage user and a task that requires querying multiple repositories together. The reviewed record does not supply that answer. Merely having multiple local repositories or worktrees does not demonstrate a cross-repository query need.

| Design | Benefits | Costs |
|---|---|---|
| Federated query over existing per-project indexes | Reuses project routing and index lifecycle; retains independent exclusions and rebuilds; can add a bounded search entry point without changing single-project queries. | Needs explicit project selection, compatible score handling, request-wide budgets, and partial-failure reporting. It does not create cross-project symbol edges. |
| Unified index with required project identity | Can support joint graph traversal and cross-project coupling if those relationships are actually modeled. | Requires project identity in every relevant storage key, query, deletion, migration, and filtering path; increases the consequence of an omitted project filter. Independent clone freshness still needs representation. |

Recommend federation if the demand gate opens for search. Unified storage is the next-best alternative only when demonstrated cross-project graph questions justify the migration. Cross-service contracts and inferred service edges remain outside this proposal. The recommendation is provisional because no qualifying workload was supplied.

### Proposed bounded federation contract

This is a design specification, not an available CLI flag or MCP tool.

1. Require an explicit list of canonical absolute project roots. Do not discover sibling repositories from remote URLs, filesystem parents, retrieved text, or indexed configuration. Preserve each root's exclusions and index state. Deduplicate identical canonical roots, but keep distinct worktrees separate even when they share a remote.
2. Start with proposed hard limits of 8 projects, 2 concurrent project searches, 200 candidates total, 20 returned rows, and a 5-second request deadline that includes queueing. These are initial design bounds, not measured optimal settings. Check cancellation before scheduling or consuming more candidates. Thread the deadline through model and storage waits; an outer response timeout alone does not bound work holding shared resources.
3. Use one compatible embedding identity for a merged semantic page. Require equality of the persisted [semantic fingerprint](../../crates/embed/src/fingerprint.rs), including artifact identity, dimension, pooling, chunking/pipeline policy, and recorded execution-provider/runtime identity. Equal model names and dimensions alone do not suffice. If fingerprints differ or are missing, return an explicit incompatibility result identifying the affected projects and a reindex/configuration remedy; do not silently mix vectors or omit a project as though the request were complete.
4. For the first implementation, merge on a retained raw semantic score from that compatible space. Never merge by per-project rank. The historical SocratiCode `38dd5543` example promoted a weak rank-1 result from one collection over a strong rank-3 result from another. Raw cosine is comparable only after the compatibility checks above. CodeSage's final [search scores](../../crates/graph/src/search.rs) also include corpus-local fusion/rescaling, boosts, penalties, reranking, and mention anchors; those final scores cannot simply be relabeled raw cosine. A future combined reranker must score the shared candidate pool once and have its own evidence gate.
5. Reserve an equal candidate share for each selected project within the total budget; report each exhausted share as a candidate truncation. Bounded per-project retrieval can omit globally relevant candidates, so the merged page must disclose its candidate limits rather than claim exhaustive top-k. Sort by raw score with deterministic project/path/span tie-breakers. Do not deduplicate equal paths or equal snippets across distinct roots: retain project provenance and show duplicated content as separate results.
6. Return per-project status, index freshness, candidates considered, truncation, and error or timeout details alongside the merged page. Reject malformed selections or incompatible vector spaces before dispatch. After dispatch, a failed project may yield an explicitly partial page from successful projects; all-project failure yields an error, never an empty success. A partial page cannot assert that no matches exist in failed projects. Missing indexes do not trigger implicit indexing, model downloads, or configuration writes.
7. Treat project names, paths, code, and rationale as untrusted data in the response. They cannot authorize additional projects or change agent instructions. The [daemon contract](../../AGENTS.md) co-trusts processes under one Unix UID; per-project indexes preserve lifecycle boundaries but do not provide a security sandbox between same-UID clients. Federation must not claim stronger isolation.

Before implementation approval, validate the bounds on the named user's workload and specify the external response schema. Before shipping, exercise mismatched fingerprints, stale and missing indexes, overlapping worktree paths, one slow project, cancellation while queued, total failure, partial failure, candidate truncation, and the weak-rank-1/strong-rank-3 merge trap. Record the workload and resulting recall/latency tradeoff. Reverse the federation recommendation if the required answer depends on explicit cross-project graph edges that a bounded search fan-out cannot provide.

Disposition: the memo deliverable is complete; implementation remains deferred. Closing this memo must preserve the implementation gate rather than report cross-repository search as shipped.
